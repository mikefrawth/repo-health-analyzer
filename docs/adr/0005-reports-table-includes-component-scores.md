# The `reports` table carries a `component_scores` column the original spec's table sketch omitted

The original spec's sketch of the `reports` table (`repo-health-analyzer-spec.md`) only listed `metrics`, `health_score`, and `ai_summary`. The frontend migration (`frontend/supabase/migrations/0002_add_component_scores.sql`, commit `fcf8175`) adds `component_scores jsonb not null`, storing the per-category 0.0–1.0 values that `component_scores(metrics)` in `backend/app/scoring.py` already computes on the way to a Health Score. This is the same class of deviation as [ADR-0004](0004-reports-table-includes-analysis-scope.md), recorded separately because it is a separate column added for a separate reason.

Reasoning: a Health Score is a single number over seven weighted categories, and without the per-category values a Report can state its score but not disclose why it is what it is. The alternative — recomputing the components in the frontend from `metrics` — is precisely what [ADR-0001](0001-deterministic-health-score.md) exists to prevent: two implementations of one formula that can silently drift. Persisting what the backend already computed introduces no new scoring logic and no second source of truth. It is also the only way a saved Report stays explicable after the fact, since Reports are immutable and the formula may change beneath them.

Trade-off: the values are stored but their **weights** are not. A reader (or a chart) that wants each component's weighted contribution has to pair `component_scores` with the `WEIGHTS` table, which currently lives only in `backend/app/scoring.py` and is mirrored by hand in `frontend/src/lib/metrics-display.ts`. That mirror is a real drift risk of the kind ADR-0001 warns about, and shipping the weights alongside the scores in `AnalyzeResponse` would close it — deferred rather than decided against.
