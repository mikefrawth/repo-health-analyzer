# Private-repo analysis resolves its GitHub token with a pure function, and treats an ambiguous 404 as a consent prompt

Issue #24 (part of the accounts/subscriptions epic, #19) let a signed-in user analyze one of their own private repositories, requesting GitHub's private-repo ("repo") OAuth scope only at the moment they actually need it — never upfront at login (ADR-0007).

## Decision

**Token resolution is a pure function, backend-side.** `backend/app/token_resolution.py`'s `resolve_github_token(user_token, user_token_scope, fallback_token)` decides which token a fetch should attempt: a signed-in user's own token when there is one (it works for public repos just as well as the server's, and gives them their own GitHub rate limit — story #4 of #19), otherwise the server's shared fallback (`Settings.github_token`), same as an anonymous request today. It takes no live GitHub call and is unit-tested with plain inputs/outputs (`backend/tests/test_token_resolution.py`), matching the pure-function convention `app/scope.py` already established.

**The frontend owns the session; the backend owns the decision.** `/api/analyze` (`frontend/src/app/api/analyze/route.ts`) is the only place that knows who's signed in — it reads the caller's stored token via a new `fetchGithubProfile()` (`frontend/src/lib/user-profiles-repo.ts`, using the session-aware `serverClient()` so RLS's owner-only `select` policy on `user_profiles` narrows it for free) and forwards `github_token`/`github_token_scope` as two new optional fields on `AnalyzeRequest`. The backend never looks up a user or a session itself — it only ever sees the token it was handed, same as it always has.

**"Needs consent" isn't decided upfront — it's what an ambiguous 404 means.** GitHub's API answers "doesn't exist" and "exists but this token can't see it" identically (404), so `resolve_github_token` can't itself know whether a private-repo prompt is warranted before a fetch is attempted. Instead, `TokenChoice.ambiguous_not_found` is true exactly when the chosen token is the user's own and its scope isn't yet `"repo"` — the one case where a 404 doesn't rule out "private, and this token just can't see it." `analyzer.analyze()` (`backend/app/analyzer.py`) catches a 404 from `fetch_repo_metadata`, and if the choice was ambiguous, re-raises with a new `AnalysisError(code="needs_private_scope")` instead of a plain not-found — `AnalysisError` gained an optional `code` field (`backend/app/errors.py`) for exactly this: an HTTP status alone can't carry a second axis of meaning, and this is the one failure in the app that needs one. `main.py`'s exception handler includes `code` in the JSON body only when set, so every other failure's shape is unchanged.

The frontend's `describeAnalyzeFailure` (`frontend/src/lib/analyze-errors.ts`) reads that `code` and, when it's `needs_private_scope`, overrides the status-based mapping — the wire status stays 404 from the backend, but the route re-answers the browser with 403 (the more accurate "more permission would help"), and a new `needs_private_scope` entry joins `AnalyzeErrorCode`. `AnalyzeForm.tsx` renders a "Grant access to private repos" link for that one code, pointing at `/auth/login?scope=private&next=<current path>`.

**The scope upgrade is a second, explicit OAuth round trip.** `/auth/login` (`frontend/src/app/auth/login/route.ts`) now accepts `?scope=private`, in which case it passes `scopes: "repo"` to `supabase.auth.signInWithOAuth` and carries both `next` and `scope` through as query params on the `redirectTo` URL — GitHub returns the browser to exactly that URL, so `/auth/callback` can read `scope` back off its own request and label the freshly stored token `"repo"` instead of the default `"public"` (`githubProfileRow()` in `frontend/src/lib/user-profile.ts` gained a third `requestedScope` parameter, defaulting to `"public"` so every existing call site is unchanged). No new migration: `user_profiles.github_token_scope` (0004) already exists specifically for this.

**A private-repo Report is quantitative-only, unconditionally — not just when Claude fails.** Per the ticket, private-repo analysis has no subscription/credit involvement in v1. `analyzer.analyze()` skips `generate_summary` entirely when the fetched metadata says `private: true`, rather than calling it and discarding the result (or worse, relying on a future credit-gate to reject it) — an intentional "skipped" free Report, indistinguishable on the wire today from a Partial Report (both are `ai_summary: null`), since #25 is what introduces a status field that tells the two reasons apart.

**The clone itself now authenticates too, without the token touching argv.** `fetch_repo_metadata` succeeding only proves API access; `clone_repository` (`backend/app/github.py`) still shelled out to an unauthenticated clone URL. It now accepts an optional `token` and, when given, sets `GIT_CONFIG_COUNT`/`GIT_CONFIG_KEY_0`/`GIT_CONFIG_VALUE_0` environment variables carrying an `http.extraheader` Authorization value (git ≥ 2.31) rather than embedding the token in the clone URL or passing `-c` on the command line — both of which would appear in `ps` output and, on a clone failure, in the git stderr this app already quotes back to the user. The stderr line included in a clone-failure message is additionally scrubbed of the literal token as a second line of defense.

## Alternatives considered

**Have the frontend decide which token to use, sending only the resolved token to the backend.** Rejected: the "ambiguous 404" signal only exists once a fetch has actually been attempted with a specific token — that has to happen backend-side, where the fetch itself lives. Splitting "which token" (frontend) from "was that a real not-found" (backend) would require the same scope information to travel to the backend anyway, just framed differently, for no gain.

**Infer scope sufficiency from the fetch result alone (e.g., retry once with an upgraded token if the first attempt 404s), rather than tracking `github_token_scope` on the stored profile.** Rejected: there's no "upgraded token" to retry with server-side — the whole point of progressive consent is that GitHub has to hand back a *new* token after the user grants more access, which only happens through a full OAuth round trip. The stored scope label is what lets the backend distinguish "this token could not possibly see a private repo" from "this token might, and just didn't."

**Preemptively request the `repo` scope for every private-repo-shaped 404, without checking `ambiguous_not_found` first.** Rejected — this is exactly the acceptance criterion #24 exists to satisfy: "a logged-in user who only ever analyzes public repos is never prompted." A user with `repo` scope already granted just needs a genuine not-found, not another consent screen.

## Consequences

- `AnalyzeRequest`/`_measure_clone`/`clone_repository` all gained an extra optional parameter for the token; every existing caller and test fake needed updating to accept (and ignore, where irrelevant) the new one — mechanical, but touches most of the analyze path's signatures.
- The heuristic is inherently approximate: a logged-in user with only public scope who mistypes a *public* repo's name will also see the "grant access" prompt, since the backend genuinely cannot tell the two cases apart from a 404 alone. Acceptable per the ticket's own framing ("repos they don't have public access to, and haven't yet granted private-repo scope for") — the alternative (always saying "not found") is strictly worse for the case that matters more.
- `#25` (credit-gated detailed reports) will need to decide how a private-repo request interacts with credit-gating once that machinery exists — today's "always skip the summary for a private repo, no gate involved" is deliberately the simplest thing that satisfies #24 alone.
